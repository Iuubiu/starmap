@mastra/core@1.78.0
6a465f9
This commit was created on GitHub.com and signed with GitHub’s verified signature.
GPG key ID: B5690EEEBB952194

Learn about vigilant mode.

Highlights

Agent Scopes (multi-tenant identity + safer memory/thread routing)

Agents now support scopes (<type>:<value>) passed per call, configured on the agent, or injected by trusted middleware via MASTRA_SCOPES_KEY; Mastra merges all three. Memory can derive resource and thread from resource:/thread: scopes (with conflicts now returning HTTP 400), nested calls can choose their own thread, and resumed runs preserve their original scopes (no adding new ones).

Trace Aggregation API (server + client + React)

Mastra adds trace aggregation end-to-end: POST /observability/traces/aggregate is discoverable via GET /observability/capabilities (traceAggregate), clients get mastraClient.aggregateTraces(), and React adds useTraceAggregateAvailable(). Field discovery now returns an aggregate schema describing valid group-by dimensions and measures.

Typed Signal Queueing for Agents (queueSignal)

You can now queue a typed signal behind the active run—without degrading it into a plain user message—via Agent.queueSignal() / session support and the new server route POST /agents/:agentId/queue-signal. Runs triggered by a signal also record signal metadata on the AGENT_RUN span for better traceability.

Faster, more usable trace lists with stored input/output/error previews

Trace and span list APIs now return outputPreview and errorPreview (and spans add errorTruncated), backed by a shared preview format in @mastra/core/storage (buildPreview, PREVIEW_MAX_LENGTH). Stores (ClickHouse/Postgres/DuckDB) persist previews at write time so queryTraces()/querySpans() no longer need to read full payloads—improving latency, memory use, and enabling UIs like Playground’s new Traces “Output” column.

Better reliability for long-running & durable workflows

Workflow execution is more robust: .foreach() failures now correctly fail the run (instead of hanging or corrupting output), durable agents are correctly honored inside workflow steps across engines, resume behavior preserves suspendData after crashes, and invalid resume data now throws AGENT_RESUME_INVALID_DATA without consuming the suspended run.

Breaking Changes

  • buildInputPreview() and INPUT_PREVIEW_MAX_LENGTH are deprecated in favor of buildPreview() and PREVIEW_MAX_LENGTH.
  • Factory sessions no longer have modes (Plan/Explore removed); thinking defaults and related config endpoints now use a single global default, and PUT /web/config/thinking rejects modeDefaults.
  • Factory credential behavior changed: cross-scope credential fallback is removed; custom credential providers must move from orgFirst to explicit credentialScope / policy resolution.

@mastra/core@1.78.0

Minor Changes

  • Added scopes to agents: the addresses a run acts as, written as <type>:<value> (for example org:acme, resource:user-123, thread:conversation-123). (#26593)

    Setting scopes. Pass them per call on stream, generate, network, sendMessage, queueMessage and sendSignal, set them on the agent, or set them from trusted middleware with the new MASTRA_SCOPES_KEY request context key. Mastra combines all three. Read an agent's configured scopes with agent.getScopes().

    Memory. Memory reads its resource and thread from resource: and thread: scopes, in addition to memory.resource, memory.thread and the existing request context keys. If they name different values, the call throws a 400 error instead of silently picking one. Runs with no scopes from any source behave as before.

    const agent = new Agent({
  id: 'support',
  model: 'openai/gpt-5-mini',
  memory: new Memory(),
  scopes: ({ requestContext }) => {
    // Set by your auth middleware. Request bodies can fill unreserved keys, so only read trusted ones.
    const orgId = requestContext.get('org-id');
    return orgId ? [`org:${orgId}`] : [];
  },
});

// Before
await agent.generate('Hi', { memory: { resource: 'user-123', thread: 'conversation-123' } });

// After
await agent.generate('Hi', { scopes: ['resource:user-123', 'thread:conversation-123'] });

    Nested calls. Tools, processors and subagents see the run's other scopes (for example org:acme) under MASTRA_SCOPES_KEY, but not its resource: and thread: scopes, so nested agent calls can choose their own thread.

    Suspended runs. Suspended runs keep their scopes when resumed: a resume may repeat some or all of them but cannot add new ones.

    Upgrading. Upgrade @mastra/server together with this release. While an older server is registered, agents refuse scopes from the call and the request context with an AGENT_SCOPES_SERVER_OUTDATED error (HTTP 400); the agent's own scopes option still applies. This detection relies on the server registering itself with Mastra, which @mastra/server has done since 1.0.0-beta.5. Servers older than that — and custom server adapters that never call mastra.setMastraServer() — are indistinguishable from no server at all, so they are not detected: upgrade them rather than relying on the guard.

    Runs suspended before this release have no recorded scope set; resuming one adopts the scopes supplied at resume time (the same trust checks as a fresh run apply) instead of rejecting them. Runs suspended after the upgrade record their set — including the empty set — and a resume may not add to it.

  • Added traceAggregateDiscoverySchema and an optional aggregate field on the trace-query fields response, describing the dimensions and measures aggregateTraces() accepts. (#27185)

  • Added queueSignal() to Agent and AgentController Session. It queues a typed signal behind the active run like queueMessage(), but keeps the signal type, tag, and attributes instead of turning it into a plain user message. (#27081)

  { resourceId: 'user-123', threadId: 'thread-abc' },
);

    Runs started by a signal now record it on the AGENT_RUN span as attributes.signal (id, type, tagName, attributes), so traces show which signal started a run.

  • Memory can now contribute error processors to an agent. MastraMemory.getErrorProcessors() works like getInputProcessors() and getOutputProcessors(): the agent appends what it returns to its resolved errorProcessors, on both regular and durable agents. These processors run after configured and default error processors, and stay in place when a call passes its own errorProcessors. The base implementation returns none, so existing memory classes are unaffected. (#26029)

    class MyMemory extends MastraMemory {
  async getErrorProcessors() {
    return [new MyRecoveryProcessor()];
  }
}

  • Added one preview format for span input, output and error. Trace lists (queryTraces(), listTracesLight()) now return outputPreview and errorPreview next to inputPreview, and querySpans() rows add errorPreview and errorTruncated. (#26567)

    New exports from @mastra/core/storage

    • buildPreview(value) builds a preview from a decoded payload, and buildPreviewFromJson(json) from stored JSON text. Both cut to PREVIEW_MAX_LENGTH (100) characters and end with … when cut.
    • Exported spans and span records accept optional inputPreview, outputPreview and errorPreview, preserved through create/update record builders. Stores trim nonblank supplied previews and cap them like generated ones (100 characters plus …, never splitting a surrogate pair); missing or blank previews are generated from the payload.
    import { buildPreview } from '@mastra/core/storage';

buildPreview({ messages: [{ role: 'user', content: 'Where is my order?' }] }); // 'Where is my order?'
buildPreview({ message: 'Tool failed' }); // 'Tool failed'

    Behavior changes

    • For a message list, previews now show the last user message instead of every user message joined with |.
    • querySpans() previews are now at most 100 characters of readable text plus an ellipsis instead of the first 256 characters of raw JSON.

    buildInputPreview() and INPUT_PREVIEW_MAX_LENGTH are deprecated. Use buildPreview() and PREVIEW_MAX_LENGTH. buildInputPreview(input, maxLength) still caps its preview at maxLength.

  • Added a beforeApproval hook to tools that require approval. It runs before the agent pauses for approval and can reject the call by returning { proceed: false, output }. The agent then skips the approval pause and does not execute the tool, and output goes back to the model as the tool result. Invalid calls are returned to the model to fix, and people are only asked to approve valid ones. (#26927)

    const issueRefund = createTool({
  id: 'issue-refund',
  inputSchema: z.object({ orderId: z.string(), amount: z.number() }),
  requireApproval: true,
  beforeApproval: async ({ orderId, amount }) => {
    const order = await orders.find(orderId);
    if (!order) return { proceed: false, output: { error: `Order ${orderId} not found` } };
    if (amount > order.paid) return { proceed: false, output: { error: `Amount exceeds ${order.paid}` } };
  },
  execute: async ({ orderId, amount }) => refunds.issue(orderId, amount),
});

    The hook does not run again when the call resumes after an approval decision. If the hook throws, the error is logged and the call proceeds to the approval gate. Keep validating inside execute too, because state can change while the call is waiting for approval.

@mastra/core@1.77.0
f88217d

Highlights

Factory Sandbox Provider Contract + New Providers (Docker/E2B/Platform)

Mastra Factory now has a first-class FactorySandbox contract for sandbox providers, enabling tunable settings schemas, repository templates, and prebuilt environment builds. New *FactorySandbox implementations ship for Docker (@mastra/docker), E2B (@mastra/e2b), and Mastra Platform (@mastra/platform-workspace) to plug in with a single provider instance.

Factory Environment Builds + Multi-Repo Sessions

Factory can now build environment templates ahead of sessions (manual, scheduled cron, or push-triggered builds) when the sandbox supports builds, reducing first-session cold starts. Sessions also boot every repository in the environment (ordered, shared workspace root) and can push/open change requests across any environment repo via source_control_* tools with a repository slug.

Durable Agent Safety: Run Fencing Across Storage Backends

Multiple storage adapters (Cloudflare DO/D1, Convex, DynamoDB, DSQL, MongoDB, MSSQL, MySQL, OracleDB, Spanner, Redis/Upstash/Valkey) now support “run fencing” so a durable execution that lost ownership (e.g., crash recovery) can’t overwrite the recovered run’s threads/messages/workflow state—significantly improving correctness in distributed deployments.

Observational Memory Concurrency + New Conflict-Aware Storage Writes

A large set of fixes harden Observational Memory against overlapping buffering/activation/reflection across processes, adding “generation” protection (supersededBy) and new write-result APIs like commitActiveObservations({ applied, reason }) and appendBufferedObservations({ persisted, recordId }). Observational memory also blocks less often (blockAfter band), preserves correct ordering, and improves reflection fidelity for long-running threads.

Trace Linking & Cross-System Observability (Spans + MCP)

Spans now support links (including W3C traceparent helpers) and exporters propagate them (Datadog/Sentry/OTel bridge/exporter), enabling correlation across traces without joining them. @mastra/mcp additionally links client tool-call spans to server request spans bidirectionally, making it easy to navigate between agent traces and MCP server traces.

Breaking Changes

  • Factory projects now support provider-instance sandboxes (MastraFactoryConfig.sandbox) for settings/builds; existing callback form still works but lacks these capabilities.
  • @mastra/server workflow HTTP routes no longer allow starting/resuming internal workflows (returns 404); durable agents must be invoked via agent routes (e.g., POST /agents/:agentId/stream).
  • AgentController thread/session behavior changes include new suspension “address” claiming APIs and deprecations: SessionRecord.modeId/modelId/state/pending, HarnessStorage.appendPendingItem/updatePendingItem/removePendingItem, and SessionSuspensions.resolveToolCallId().
  • @mastra/playground-ui: Dialog/AlertDialog removed handle/render-style props; components are now controlled via open/onOpenChange.
  • @mastra/client-js / @mastra/react compare-experiments APIs deprecate experimentIdA/experimentIdB in favor of experimentIds (+ optional baselineId).

    import { FactorySandbox } from '@mastra/core/workspace';
import type { FactorySandboxContext } from '@mastra/core/workspace';
import type { PublicSchema } from '@mastra/core/schema';

interface Settings {
  region?: 'us' | 'eu';
}

  readonly provider = 'my-cloud';
  readonly settings: PublicSchema<Settings> = {
    type: 'object',
    properties: { region: { type: 'string', enum: ['us', 'eu'], default: 'us' } },
    additionalProperties: false,
  };

  create(ctx: FactorySandboxContext, settings: Settings) {
    return new MyCloudSandbox({
      id: ctx.sessionId,
      sandboxId: ctx.sandboxId,
      template: this.template(ctx, settings),
      workingDirectory: ctx.workingDirectory,
      region: settings.region ?? 'us',
    });
  }

  // Optional: the sandbox template image Factory can build ahead of time
  template(ctx: FactorySandboxContext, settings: Settings) {
    return myCloudTemplate(ctx, settings);

  // Optional: build that template ahead of time and report on it
  readonly builds = {
    start: async (ctx: FactorySandboxContext, settings: Settings) => myCloud.startBuild(this.template(ctx, settings)),
    get: async (ctx: FactorySandboxContext, settings: Settings, buildId: string) => myCloud.buildStatus(buildId),
    list: async (ctx: FactorySandboxContext, settings: Settings) => myCloud.builds(this.template(ctx, settings).name),
  };
}

@mastra/core@1.76.0
81299c9

Highlights

Durable agent run ownership + storage-level run fencing

Crash recovery is now safe across multiple instances: runs are claimed by the execution driving them, recovery skips live-claimed runs (or can force take over), and storage adapters can enforce “run fences” to reject writes from an execution that lost ownership—preventing message/thread/workflow state corruption.

Atomic working-memory merges on PostgreSQL (and explicit merge mode over HTTP)

Concurrent schema-based working memory updates no longer stomp each other in Postgres: with scope: 'resource', partial updates are deep-merged inside a row-locked transaction. You can also explicitly mode: 'merge' via the server/client APIs, and unsupported adapters now fail with a clear 400 instead of silently replacing records.

File-handling resilience + sandbox-first file workflows

Agents no longer get “stuck” when a provider rejects an attached file: the new default UnsupportedFileHandler retries with the file removed (or replaced by a sandbox path when available). For file-centric tool workflows, the new FileUploadProcessor can upload eligible user files into the workspace sandbox and pass the model a sandbox path instead of raw file content.

Observational Memory now supports native model: 'auto' (new default)

Observer/Reflector model selection can follow the active main model/provider automatically per call, while explicit model IDs stay pinned. This is now the default for OM (model, observation.model, reflection.model), with hooks (autoModels, resolveModel, resolveAutoModelId) to control how “auto” resolves in your environment.

New observability nesting + richer trace search

tracingOptions.nestUnderParent (and nestUnderRun()) lets you attach a run as a true child span under an earlier run in the same trace (e.g., LLM judges), preserving the parent run’s trace-level identity. Trace querying also gains word/phrase matches / notMatches operators (across stores/types), and metrics add a usageId to group token/cost rows per model call.

Breaking Changes

  • @mastra/playground-ui: old Metrics card views/components were removed in favor of the new self-contained Metrics cards/dashboard building blocks.
  • @mastra/playground-ui: MetricsCardGroup no longer accepts variant; MetricsLineChart dropped xAxisInterval/xAxisMinTickGap.
  • @mastra/memory Observational Memory defaults changed: OM now defaults to model: 'auto' (instead of google/gemini-2.5-flash), which may select a different provider/model depending on available credentials.

@mastra/core@1.76.0

Minor Changes

  • Concurrent schema-based working memory updates no longer lose each other's fields when using PostgreSQL. With scope: 'resource', the update tool now deep-merges partial updates inside a row-locked transaction, so writers in separate processes that change different fields all keep their changes. Other storage adapters keep the existing in-process behavior. (#25848)

    You can also merge from your own code or over HTTP:

    await memory.mergeWorkingMemory({ threadId, resourceId, workingMemory: { city: "Berlin" } });

await client.updateWorkingMemory({
  agentId,
  threadId,
  resourceId,
  workingMemory: JSON.stringify({ city: "Berlin" }),
  mode: "merge"
});

    Merges are rejected (HTTP 400 from the server) when the storage adapter doesn't support atomic merges, instead of silently replacing the record.

    Also in: @mastra/client-js@1.53.0, @mastra/memory@1.37.0, @mastra/pg@1.31.0, @mastra/server@1.76.0

  • processLLMRequest now receives the workspace of the step, the one the agent's tools use, so a processor can work with the agent's sandbox or filesystem before a model call. (#25814)

    const processor: Processor = {
  id: "my-processor",
  async processLLMRequest({ prompt, workspace }) {
    if (workspace?.hasSandboxConfig()) {
      // ...
    }
  }
};

  • Added threadMetadata to the onDelegationStart return value so delegated sub-agent threads can carry metadata such as a tenant ID. The metadata is applied when the sub-agent thread is created, which makes those threads findable with metadata-filtered queries. (#25200)

    await supervisor.generate("Summarize the report", {
  memory: { thread: "parent-thread", resource: "user-1" },
  delegation: {
    onDelegationStart: () => ({ threadMetadata: { tenantId: "acme" } })
  }
});

await memory.listThreads({ filter: { metadata: { tenantId: "acme" } } });

  • Fixed durable agent crash recovery re-running runs that were still executing. Recovery restarted every run left in the running state, even when another process was still driving it. Both executions then wrote to the same thread, and the original one could overwrite the recovered assistant messages (#23734). (#26418)

    Each run is now claimed by the execution driving it: stream(), generate(), resume(), or recover(). The claim is renewed while the run executes and lapses about 30 seconds after its process dies.

    • recoverActiveRuns() skips runs whose claim is still live. Skipped runs are returned with status: 'skipped', a reason, and, for a run live in another process, a retryAt time.
    • mastra.recoverAllDurableAgents() counts skipped runs in a new skipped field and checks each one again once its claim could have lapsed, so a run whose process crashed is still recovered.
    • recover() throws DURABLE_AGENT_RUN_ACTIVE for a live run. Pass force: true to take the run over. The execution that held it stops.
    • recover() throws DURABLE_AGENT_RECOVER_RUN_ACTIVE_LOCALLY for a run the same process is still executing, even with force: true. Previously it started a second execution of the run. Wait for the run to finish instead.
    • Starting a run with a runId that another execution holds waits up to 5 seconds, then throws DURABLE_AGENT_EXECUTION_CONFLICT.
    • mastra.shutdown() releases runs still executing after the drain window, so the next boot recovers them right away.
    • Run streams drop events from an execution that lost its run. With a storage adapter that supports run fencing, that execution's writes are also rejected, so it can't overwrite messages, threads, or workflow state. A warning is logged when the workflows or memory store doesn't support run fencing: whenever runs are recovered, through recoverActiveRuns() or recover(), and, with recovery: { durableAgents: 'auto' }, when a run starts.
    const { recovered } = await durableAgent.recoverActiveRuns();

for (const run of recovered) {
  if (run.status === "skipped" && run.reason === "run-active") {
    console.log(`${run.runId} is still running. Check again at ${new Date(run.retryAt!)}`);
  }
}

// Take a run over even though another execution still holds it
const stream = await durableAgent.recover(runId, { force: true });

    See Run ownership for how claims are enforced and how recovery works across multiple instances.

@mastra/core@1.69.0

Minor Changes

  • Added classifier registration on Mastra. (#24738)

    Classifiers can now be passed to new Mastra({ classifiers }) and accessed with getClassifier, getClassifierById, listClassifiers, addClassifier, and removeClassifier. Registered classifiers evaluated without an active trace start a root CLASSIFIER_EVALUATION span through the Mastra instance's configured observability provider.

    const mastra = new Mastra({ classifiers: { router } });
const classifier = mastra.getClassifier('router');

  • Added configured classifiers as typed workflow steps with fluent and dynamic graph support. Classifier steps expose complete typed answers and token usage for existing branch and conditional control flow. (#24747)

    workflow
  .map({ message: { initData: true, path: 'message' } })
  .classifier(router)
  .branch([
    [async ({ inputData }) => inputData.answers.route.choice === 'billing', billingStep],
    [async ({ inputData }) => inputData.answers.route.choice === 'support', supportStep],
  ]);

  • Deprecated the group option on the trace-query request contract. Grouping remains functional until the next major release; use the queryThreads thread-query contract for new code (exposed as queryTraceThreads() in @mastra/client-js). (#23790)

    Before:

    import type { TraceQueryRequest } from '@mastra/core/storage';

const request: TraceQueryRequest = { timeRange, group: { by: ['threadId'] } };

    After:

    import type { QueryThreadsInput } from '@mastra/core/storage';

const input: QueryThreadsInput = { traces: { timeRange } };

  • Added context.background.adopt() so tools can return an acknowledgement while native background tasks track their existing operation through completion and cancellation. (#24418)

    Previously, background tools had to keep execute() pending:

    execute: async (input, context) => {
  const operation = startResearch(input, context.abortSignal);
  return await operation.finished;
};

    Tools can now adopt their operation during native background execution:

    execute: async (input, context) => {
  const operation = startResearch(input, context.abortSignal);
  if (context.background) {
    context.background.adopt({
      completion: operation.finished,
      cancel: reason => operation.cancel(reason),
    });
    return { answer: 'Research started' };
  }
  return await operation.finished;
};

    startResearch represents the tool's operation API. Its finished promise must resolve with the final tool result after cleanup, or reject on failure. Adopt once, before execute() returns. The handle stays in memory and cannot resume after a process restart.

  • Added rootSpanName to tracingOptions so each agent or workflow run can set its own root span name. Runs of the same workflow no longer all show up as workflow run: 'my-workflow' in trace lists. (#24564)

    await run.start({
  inputData: { skillId: 'typescript' },
  tracingOptions: { rootSpanName: 'skill-analyze: typescript' },
});

    The name applies to the root span only. Child spans keep their default names, and entity filters still match on the workflow or agent id. Related: #24518

    Also in: @mastra/observability@1.18.0, @mastra/server@1.69.0

  • Added ClassifierProcessor for applying typed classifier policies to agent input, output, and streaming content. (#24768)

    import { Agent } from '@mastra/core/agent';
import { Classifier } from '@mastra/core/classifier';
import { ClassifierProcessor } from '@mastra/core/processors';

const safety = new Classifier({
  id: 'safety',
  model,
  questions: {
    unsafe: { type: 'boolean', criteria: { true: 'Unsafe', false: 'Safe' } },
  },
});

const agent = new Agent({
  id: 'support-agent',
  name: 'Support agent',
  instructions: 'Answer support questions.',
  model: 'openai/gpt-5-mini',
  inputProcessors: [
    new ClassifierProcessor({
      classifier: safety,
      onResult: (answers, { abort }) => {
        if (answers.unsafe.probability > 0.8) abort('Rejected by safety policy');
      },
    }),
  ],
});

  • Added a typed Classifier primitive for fixed-option evaluation with AI SDK evaluation models. (#24458)

    import { Classifier } from '@mastra/core/classifier';

const classifier = new Classifier({ id: 'router', model });
const result = await classifier.evaluate({
  state: request,
  questions: {
    route: {
      type: 'choice',
      criteria: { support: 'Support request', sales: 'Sales request' },
    },
  },
});

  • Added validateSkillContent() and exported validateSkillMetadata() from @mastra/core/skills, so apps can validate a SKILL.md before saving it using the same rules applied at load time. (#24766)

    import { validateSkillContent } from '@mastra/core/skills';

const result = validateSkillContent({ content: skillMarkdown, directoryName: 'my-skill' });
if (!result.valid) console.error(result.errors);

Patch Changes

  • Update provider registry and model documentation with latest models and providers (7fefefd)

  • Fixed deferred aborts for paused tool calls and tool approvals. They no longer stop a new run started after switching threads or running /new. (#24743)

  • ClassifierProcessor now fails closed by default. When the classifier call fails, the request is aborted instead of letting unchecked content through. Pass errorStrategy: 'warn' to keep the previous fail-open behavior: (#24793)

    new ClassifierProcessor({ classifier, onResult, errorStrategy: 'warn' });

  • Honor tracingOptions.rootSpanName when creating a root span. The caller-supplied name replaces the default agent run: '<id>' or workflow run: '<id>' name on the root span only. Works for the default and Inngest workflow engines because the name is applied when the span starts, before any durable snapshot is taken. (#24564)

    const span = observability.startSpan({
  type: SpanType.WORKFLOW_RUN,
  name: "workflow run: 'skill-analyze'",
  tracingOptions: { rootSpanName: 'skill-analyze: typescript' },
});

span.name; // "skill-analyze: typescript"
