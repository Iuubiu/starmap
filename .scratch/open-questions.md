## 一、阻塞架构的问题

### OQ1｜Mastra 的 skill 载体到底是什么形态（阻塞级）

**背景**：用户坚持「skill 打包在应用里、接入 Mastra，不该有 DSH 的事」。但 Mastra 官方抽象是：
- `Agent` — 有 instructions、tools、memory、workflows
- `Tool` — 有 inputSchema / outputSchema / execute
- `Workflow` — 有 step、状态机、`.then()/.branch()/.parallel()`

**Mastra 没有名为「skill」的一等抽象。** Anthropic Agent Skills 是**文件系统约定**（SKILL.md + frontmatter + progressive disclosure），本质靠**模型的文件读取能力**加载。

**需要裁决的是**：我们的「skill」在代码里长什么样？

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| (a) skill = Tool + 描述性元数据 | 每个 skill 编译成一个 Mastra Tool，附带 name/description/purpose 供 UI 展示 | 直接用 Mastra 原生抽象；类型安全；UI 可枚举 | 失去 progressive disclosure（描述即全部） |
| (b) skill = 文件系统目录 + 运行时 loader | 保持 SKILL.md 格式，Mastra 侧写 loader 注入到 agent instructions | 可迁移性最好；与社区格式兼容 | 需要自己实现 loader；类型弱；Mastra 原生不支持 |
| (c) skill = Workflow | 每个 skill 是一个可执行流程 | 状态机明确；适合「苏格拉底追问」这类多步逻辑 | 不适合「知识/提示词型」skill；粒度太重 |
| (d) 混合：能力型=Tool，知识型=文件目录，流程型=Workflow | 按 skill 性质分流 | 各取所长 | 三套机制，认知负担 |

➡️ **倾向 (d)**，但需 Mastra 调研回来后才能定。等 `b511daea`。

### OQ2｜数据库选型（阻塞级）

**约束**：本地单用户、无登录、要「应用内自建数据库」、以后接学校数据库、需要向量检索（D6 依赖）。

| 方案 | 优点 | 缺点 |
|---|---|---|
| (a) SQLite + sqlite-vec | 零运维、单文件、可迁移；sqlite-vec 是 C 扩展，Node 有绑定 | 向量检索性能弱于专用库；并发写弱（单用户无所谓） |
| (b) SQLite + LanceDB（嵌入式） | 向量能力强；Lance 列式格式 | 两套存储，一致性需自己保证 |
| (c) PostgreSQL + pgvector | 一步到位、生态最成熟、OmniDev 默认栈 | **需要装 PG 服务**，与「本地单用户零运维」冲突 |
| (d) SQLite + 内存向量索引（暴力搜索） | 最简单；知识点数量级（~2000）暴力搜索完全够用 | 无 ANN 加速，但 2000×768 维暴力搜索 <10ms |

➡️ **倾向 (d) 起步，(a) 作为规模化路径**。理由：NestJS/Mastra 栈里 PG 会引入运维负担；知识点数量在千级，暴力搜索足够；OmniDev 默认 PostgreSQL 是**新项目默认**，但这里是本地单用户桌面应用，项目实际约束优先。

⚠️ 需确认：Mastra 的 memory 层（`@mastra/memory`）支持哪些存储后端 —— `pg_mem.ts` 里疑似有 PG memory 实现，若 Mastra 只有 PG 实现则 (c) 会被迫。

### OQ3｜教材解析管线（阻塞级）

**约束**：128 个 PDF / 1.14 GiB；需要遍历全部细节提取知识点/考点/题型；教材以「核电子学」「电子技术基础 数字部分」为核心。用户坚持「不要扫一遍就完」，要**遍历全部细节**。

**难点**：
1. **PDF 里公式极多**（核电子学、数字电路），纯文本抽取会把公式碾成乱码。
2. **图表极多**（电路图、波形图、能谱图），文本管线拿不到。
3. 教材是中文繁体/简体混排 + 大量数学符号。

**需要裁决**：
- (a) 纯文本 + 公式单独处理（用 MinerU / marker 之类 PDF→Markdown 工具，保留 LaTeX 公式）
- (b) 多模态直读（把 PDF 页面转图片，用视觉模型解析）
- (c) 混合：文本用 (a)，图表用 (b)
- (d) 先人工圈定核心章节，只精解析这部分

➡️ **倾向 (a) 起步 + (c) 作为目标**。MinerU（上海 AI Lab）对中文 PDF + 公式支持最好，但需 GPU 或较慢的 CPU 推理；本机核显接近 GTX 1550，可能够用但慢。

⚠️ 这是**最大的不确定性**，也是工作量最大的部分。需先做小样本验证（挑一本教材的一章跑通）。

## 二、影响体验的问题

### OQ4｜「数据库展示页」的具体范围

**必须回答**：展示哪些表？只读还是可编辑？要不要 SQL 控制台？

| 选项 | 说明 |
|---|---|
| (a) 只读的「数据浏览器」 | 列出各表 + 分页浏览 + 搜索；不可编辑 |
| (b) (a) + 掌握度仪表盘 | 加上掌握度可视化（每知识点 achieved/current） |
| (c) (a) + 知识库检视 | 加上 chunk 列表、答案块标记、检索测试（输入 query 看命中什么） |
| (d) 全套 + SQL 控制台 | 可执行任意查询 |

➡️ **倾向 (b) + (c) 的关键部分**：数据浏览器 + 掌握度可视化 + **检索调试器**（这是 D6 的可观测性前提，不是可选项）。**不做 SQL 控制台**（单用户本地，用 DB 工具更顺手）。

### OQ5｜「skill 库展示页」的具体范围

**必须回答**：展示什么？能不能在 UI 里启用/禁用/编辑？

| 选项 | 说明 |
|---|---|
| (a) 只读列表 | 名称、描述、触发条件、版本；点开看详情 |
| (b) (a) + 启用/禁用开关 | 用户可关掉某些 skill |
| (c) (b) + 在线编辑提示词 | UI 里直接改 skill 内容并保存 |
| (d) (c) + 导入/导出 | 打包成文件导出、从文件导入 |

➡️ **倾向 (b)**。理由：用户说「方便管理和迁移」——(b) 覆盖「管理」，迁移由文件系统天然支持（若 OQ1 选 (b) 方案）。在线编辑提示词风险高（改坏了系统没法用），且与「skill 是应用的一部分」的定位矛盾。

### OQ6｜知识点粒度到底多细

**约束**：需求 10「每个知识点下有更细粒度划分」；需求 11「提取知识点/考点/题型多层细粒度」。但 OQ3 未定时无法给出数量。

**需要裁决的是层级模型**：
- (a) 三层：学科 → 知识点 → 微知识点
- (b) 四层：学科 → 模块 → 知识点 → 微知识点
- (c) 两层：知识点 → 微知识点（学科只是标签）

➡️ **倾向 (b)**。理由：三层不够表达「A 主干 / B 探测 / C 专题 / D 实验」的分类（需求 48），四层能让模块层承载这个分类。但需课程分级调研回来后确认中国高校实际课程结构。

### OQ7｜掌握度百分比的具体口径

**约束**：需求 2「掌握度要有详细的百分比」。D2 已定双字段，但**百分比怎么算**未定。

- (a) 直接展示 BKT 后验概率（如 73.4%）
- (b) 展示证据量加权的置信区间（如 73% ± 12%）
- (c) 展示「已掌握变式数 / 目标变式数」（如 7/12 个变式通过）

➡️ **倾向 (a) 为主 + (b) 的置信度用视觉编码**（如百分比数字 + 轻微透明度/进度环）。理由：用户要「详细百分比」，纯 (c) 不够「详细」，纯 (a) 会制造虚假精确感。

⚠️ 需注意：**每节点 ≥8 次作答才允许报掌握**（表 3），所以早期百分比应显示为「证据不足」而非数字。

### OQ8｜deepseek-v4.1-flash 的 JSON 结构化输出可靠性

D6/D7 都依赖**严格 JSON 输出**（`type` / `target_gap` / `mastery_signal` / `visible_response` 必须以 `?` 结尾）。若模型不稳定支持，需要：

- (c) 换支持 structured output 的模型

### OQ9｜本地 qwen3.8flash 能否承担哪部分工作

**背景**：本机有免费模型，核显接近 GTX 1550。

可能的角色：
- (a) 只做离线批量任务（知识点提取、题目生成）
- (b) 做运行时轻量任务（意图分类、掌握度判断）
- (c) 全部不用，只用 d1api

➡️ **倾向 (a)**。理由：核显跑 8B 级模型推理速度勉强，做交互式对话体验会很差；但离线批量跑一夜完全可以。需实测速度。

### OQ10｜Mastra 的 Workflow 是否够表达「苏格拉底追问状态机」

D7 要求八级求助阶梯 + 非 LLM 策略核心。这需要：
- 显式状态（当前阶梯层级、已给提示数、掌握度信号历史）
- 分支（学生答对/答错/放弃/直接要答案）
- 循环上限（不能无限追问）

Mastra Workflow 有 `.branch()` 和状态，但**是否支持循环**需确认。若不支持，需外层包 while 或改用 Agent + tool loop。

### OQ11｜初始水平判定的具体机制

D12 已定「必须判定 + 分类分化」，但**怎么判定**未定：

| 方案 | 说明 | 风险 |
|---|---|---|
| (a) 自陈 + 少量探测题 | 问「你学过电路/数电吗」+ 3–5 题自适应 |
| (b) 纯自适应前测（CAT） | 完全客观，从中间难度开始按作答调整，约 10–20 题 |
| (c) 读教材/课程背景自陈 + 图上层级自选 | 用户自己在地图上指「我大概学到这」 |
| (d) 边学边判（不做前置判定） | 首关按最保守起点，根据表现快速调整 |

➡️ **倾向 (d) + (a) 混合**：不做长前测（前测虽有效，但首次使用就考 20 题体验极差且违背「正反馈不可缺失」），改为**首关即探测**：用教学关卡的第一步作为探测，答对就快速跳级。**待文献确认**：CAT 收敛所需题量、自陈量表与客观测验的相关系数。

### OQ12｜三档模拟学习者的 persona 与评估指标

D13 已定要建三个测试子智能体，但未定：
