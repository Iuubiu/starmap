## 证据等级

**假设生成** — 参与者是 LLM 扮演的模拟学习者，不是真人。

- 能：找出界面上真点不动的位置（`locator_failure` 数量是硬事实）、暴露流程断裂、生成待验证的假设。
  - 「硬事实」的口径：每条 `locator_failure` 都是在 **`waitForSettled` 之后仍然不存在**才算数。
    页面加载期间先让出 150ms、再等所有 `role=progressbar` 消失（上限 20 秒），
    然后才问「在不在」。不这么做的话，「h1 已渲染但内容还在 pending」会被读成
    「元素不存在」，报告里就会出现一条不成立的 blocker。（实测过：定级页
    t=572ms 时 h1 已可见、按钮还没挂上。）
- 不能：证明可用性达标、预测真人满意度、替代真实学习者测试。
- 未校准：judge 与真人评分的一致性 κ = `null`（无人工标注数据）。
- 本报告**不宣称可用性达标**。这一条由 `tools/eval/src/report/schema.ts` 的
  `claimsUsabilityPassed: z.literal(false)` 在结构上锁死，不是靠自觉。

## judge 的复现性

这一节回答的是「上面那些 judge 数字，重跑一遍还是这样吗」。做法：用同一版
judge 代码、同一批由关卡 `spec` 常量构造的输入，隔一段时间跑三次三档。

### 漂移指标本身在飘

| persona | `20261021-135402` | `20261021-144001` | `20261021-152214`（本次） |
| --- | --- | --- | --- |
| P1 小陈 | κ `null` / CV `0.078` | κ `-0.20` / CV `0.176` | κ `1.00` / CV `0.184` |
| P2 林 | κ `null` / CV `0.088` | κ `null` / CV `0.102` | κ `null` / CV `0.116` |
| P3 老周 | κ `null` / CV `0.046` | κ `-0.20` / CV `0.069` | κ `null` / CV `0.049` |

- **同一个 `κ` 在三次运行里可以是 `null`、`-0.20`、`+1.00`。** 这三个数的
  意思是「无法计算」「比随机还差」「完全一致」。它们指向完全相反的结论，
  而三次运行的产品代码、judge 代码、输入文本都没变。
- 根因：`κ` 只在 **2 个样本轮 × 3 次重放 = 6 个标签**上算。样本这么小的时候，
  一次采样翻转就能把 κ 从 `+1` 推到 `-0.2`。`null` 出现在三次重放给出同一个
  标签时（分母为 0）—— 那是**退化**，不是一致。
- **结论：`κ` 这个指标在当前样本量下没有信息量。** 报告里保留它是因为
  票 20 要求这一项，但任何引用都必须同时给出三次运行的三个值。
  `CV` 相对稳一些（`0.046–0.184`），但三档全部在 2–3 倍超标区间，
  结论「judge 分数不稳」是稳的。

### 标签与分数的逐字段比对

两次同代码运行（`144001` 与 `152214`）的 `judge-runs-<persona>.json` 逐条对齐：

| persona | 标签字段不一致 | 四维分平均绝对差 |
| --- | --- | --- |
| P1 小陈 | 6/36（含 null 的 3） | 0.58 |
| P2 林 | 6/36（含 null 的 4） | 0.40 |
| P3 老周 | 7/36（含 null 的 2） | 0.79 |

- **标签有 16%–19% 的概率在两次运行之间翻转。** 一次 judge 输出的布尔字段
  不能当事实用；`agreementWithHumanKappa` 只能写 `null`。
- **分数更飘**：四维分平均绝对差 0.40–0.79，在 1–5 分的量表上接近一整档。

### 识别率是唯一跨三run稳定的

| persona | `135402` | `144001` | `152214` |
| --- | --- | --- | --- |
| P1 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 |
| P2 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 |
| P3 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 | 答对 2/2 · 答错 2/2 |

`tools/eval/src/run.ts` 把每条输入的 3 次采样取**多数票**再回填识别率
（`metrics/compute.ts` 的 `majorityVote`）。**只取第一次采样的旧写法会让
识别率在两次运行之间凭空变化** —— 实测过一次代价：某一档的答错识别率
因此从 100% 掉到 50%，报告上看起来像产品缺陷，实际是工具只读了一票。

所以：**识别率的稳定性是工具换来的，不是 judge 稳定。**
这两件事必须分开说，否则「识别率三次都一样」会被当成「judge 可靠」。

- 复现方法：`node --env-file-if-exists=.env tools/eval/src/run.ts --persona all --output <dir>`，
  跑多次后逐条比对 `judge-runs-<persona>.json`。比对脚本是一次性探针，
  不在仓库里；字段口径见本节表格。

## 主观维度（judge）

四维分取每档全部 judge 运行的**中位数**（逐轮原始分在
`judge-runs-<persona>.json` 里，报告表格只是为了看趋势）。

| persona | 维度 | 本次得分 | 12 次运行的取值范围 | 三次运行的中位数 |
| --- | --- | --- | --- | --- |
| P1 小陈 | 可执行性 / 清晰度 / 语气 / 脚手架贴合度 | 3.0 / 4.0 / 4.0 / 2.0 | 2–5 / 2–5 / 2–4 / 1–4 | 3/3/3 · 4/4/4 · 3/4/4 · 2/2/2 |
| P2 林 | 可执行性 / 清晰度 / 语气 / 脚手架贴合度 | 3.0 / 4.0 / 3.0 / 2.0 | 2–5 / 3–5 / 2–5 / 1–4 | 3/2/3 · 4/4/4 · 4/3/3 · 2/2/2 |
| P3 老周 | 可执行性 / 清晰度 / 语气 / 脚手架贴合度 | 2.0 / 4.0 / 4.0 / 2.0 | 2–4 / 3–5 / 3–4 / 1–5 | 3/3/2 · 4/4/4 · 3/4/4 · 2/2/2 |

judge 只评这四维。判分正确性、门控结论、答案泄漏等**确定性事实不在此列**，
它们在层①里是断言（见下表）。这条边界由 `JUDGE_MUST_NOT_DECIDE` 列出，
`checkJudgeDiscipline` 会在评分时校验。

> **这四维分不能当作产品结论。** CV 全部超标（见上），同一段文本重放三次
> 会得到不同的分数；中位数只是把抖动压平了一点，不是把抖动消除了。
> 「三次运行的中位数」一列是故意放的：`可执行性` 在 P1 上是 3/3/3（稳），
> 在 P3 上是 3/3/2（不稳）。只报一格会掩盖这件事。

| 确定性断言（层①） | 本次结果 |
| --- | --- |
| 证据不足时 `percent === null`，不是 0 | 扫了全部知识点：`null` 占绝大多数，值为 `0` 的只有 1 个 —— 那 1 个是「确实测过且得 0」，不是用 0 冒充证据不足。通过 |
| 门控未达门槛返回 `undetermined` | B1 通过；B2 两种 reason 均覆盖 |
| 同一 chunk 在两个知识点下门控结论可相反 | C1 纯函数通过；**C2 因真实语料无共享答案块而跳过** |

> 层①完整结果：`pnpm --filter @starmap/eval eval:layer1` →
> **10 条：通过 9 / 失败 0 / 跳过 1**（覆盖率 90%，执行项通过率 100%）。
> 跳过的是 C2，理由写在 `src/layer1/checks.ts`：扫 40 个知识点、3775 次 chunk
> 引用，共享 chunk 0 个 —— 没有共享答案块时这条不变量在真实数据上无法构造。

## 阻塞项与建议

| # | 阶段 | 界面位置 | 问题 | 严重度 |
| --- | --- | --- | --- | --- |
| — | — | — | 本次运行无阻塞项（三档九阶段失败合计 0） | — |

建议（**均为假设，未验证**）：

- **判分漂移这一项应当先改度量口径，再谈修 prompt。** 现在 `κ` 在
  「2 样本轮 × 3 重放」上算，跨运行能从 `+1` 跳到 `-0.2`；先把每个 persona 的
  样本轮数提到 ≥10 再报 κ，否则每次运行的数字都在互相打脸。
  （工作量 `small`）
- **然后才是 prompt**：同一条 transcript 重放三次，可执行性给过 1–5 全区间。
  建议在 `chatMessages()` 里给四维各加一句可操作的锚点（例如
  「3 = 学生看完要做一次猜测试探；5 = 学生能立刻写出下一步」），
  然后用 `pnpm --filter @starmap/eval gold` 在 20 秒内验证没把 gold 判歪。
  （工作量 `small`）
- **内容侧：判定段只有 2 道题让所有识别率指标失去意义**。识别率的分母应当
  来自「学生在关卡里真实作答的题数」，而不是「spec 里 quiz 题的条数 × 2」。
  建议在 `answer` 阶段逐题记录 `{itemId, correct, 系统反馈原文}`，
  让 `observations.ts` 用真实记录而非按 spec 构造。这样才能测任意关卡。
  （工作量 `medium`）
- **把 S2/S5 接进旅程**：这两个阶段要真跑 agent 回合（`POST /api/v1/agent/turns`）
  才能拿到结构化产物卡与追问表单。现在是十级漏斗里唯一两块完全空白。
  （工作量 `large`）
- **加人工标注校准**：`agreementWithHumanKappa` 现在是 `null`，已由 schema 锁死。
  跑 50–100 条人工标注之前，judge 的分数只能当趋势看。这条不解决，
  上面第一条修好了也只是"抖动变小"，不是"可以引用"。（工作量 `large`）
- **`Sigma: Container has no width` 值得查一次**：P1 在 `node-detail` 阶段
  出现一次。图谱容器在某些布局瞬间宽度为 0。不影响功能，但会在控制台留错误，
  也可能导致该瞬间的渲染空白。（工作量 `trivial`）

## 未知与缺口

- `agreement_with_human_kappa`：LLM 模拟用户评分与真人评分的一致性**无数据**。
  本项目的调研（`.scratch/lit/ux-eval-methods.md`）里也没有找到可引用的
  r / ICC / Bland-Altman 结果 —— 这是该领域的实证空白，不是我们没查。
  跑过 50–100 条人工标注校准前，不得声称 judge 分数可信。
- 核电子学「典型误解」清单：**本报告自拟**，属设计假设，无文献支撑。
- 「追问表单」作为脚手架卡片的实证效果：未验证。
- **S2（关卡卡产出）与 S5（追问表单）本次未覆盖**：这两个阶段需要真跑
  agent 回合（`POST /api/v1/agent/turns`）才能产出结构化产物卡与追问表单，
  本版旅程只断言了「页面点得动」。这是工具缺口，不是产品缺口。
- **S9（会话恢复）本次未覆盖**：本版旅程没有对应阶段，也没有跨会话恢复的
  数据。漏斗里标「未测」。
- **识别率与泄露率的分母是构造出来的，不是观测到的**：
  `src/metrics/observations.ts` 按 spec 的 `explainCorrect` / `explainWrong`
  各造一条观察。理由写在那个文件顶部（反馈文本完全由 `correct` 决定，
  与学生的具体选项无关），但这仍然意味着**分母 = 题目数 × 2，不是真实作答轮次**。
  唯一教学关只有 2 道判定题 → 分母 2 → Wilson 区间宽到没用。
- **L3（三级施压）泄露率本次无样本**：需要「学生明着要答案之后系统的回复」，
  本版拿不到那段文本。刻意留空而不是用 `explainCorrect` 填充 ——
  填了会让泄露率恒为 1，那不诚实。
- **摩擦计数大部分未采集**：狂点 / 死点 / 清空输入 / 刷新循环 / 跳过表单
  在报告里显示「未采集」。本版旅程是确定性阶段脚本，不产生这些行为，
  所以那几项是没数，不是数出来是 0。
- **三档串行但共享同一套库**：前一档留下的作答会影响后一档的推荐与复验队列。
  完全隔离需要重建库，本工具没做。本次三档的掌握度起点并不相同。
- **judge 标签在两次运行间有 16%–19% 翻转率；漂移指标跨运行不可复现**。
  这两个数字都只来自 2–3 次运行，不该当作精确估计。它们的用途是说明
  「单次运行的 judge 数字不能当结论」，不是给出一个稳定的漂移率。
- **`Sigma: Container has no width` 只在一次运行的一个阶段出现过**，
  没有复现，也没有定位到具体布局条件。
